# PGO — Profile-Guided Optimisation, Measured Before It Is Adopted

Status: **measured 2026-10-25; not adopted (§6)** · Part of M12 in
[`PERFORMANCE-ROADMAP.md`](PERFORMANCE-ROADMAP.md), written before its code, as this
repository does it · Author: Karthikeyan NG · 2026-10-25

## 1. The question

Go builds can use a CPU profile to guide inlining and devirtualisation (`-pgo`). M12
records that PGO appears nowhere in this repository. This document asks one question:
**does a profile make the engine measurably faster on the gate's own benchmarks,
without changing what it computes?** The decision rule is in §5, written before any
number exists.

## 2. What PGO can and cannot reach here

These were checked on go1.23.5, darwin/arm64, before writing this:

- **A library cannot ship it.** The compiler applies a profile while building a main
  package, and an importer's build uses the importer's own `default.pgo`. A profile
  committed in `pkg/` changes nothing for anyone who does `go get`. Whatever §6 finds,
  the README may not say that the library "uses PGO".
- **`go test -c` ignores `default.pgo`.** A test binary built with a `default.pgo` in
  the package directory is byte-identical to one built with `-pgo=off`. Only an
  explicit `-pgo=<file>` changes it. So the bench gate, which builds both arms with
  plain `go test -c`, cannot see a committed profile at all.
- **A main package picks it up.** `cmd/obgw` built with a `default.pgo` beside it
  records `-pgo=…/default.pgo` in its build info.

So the binaries a profile can reach are the ones this repository builds and ships:

| Binary | Who runs it |
|---|---|
| `cmd/obgw` | the reference venue, the exchange-in-a-box image |
| `cmd/libobook` | the C ABI, and so every `obook` wheel on PyPI |
| `cmd/flash1engine` | flash1's harness |
| `cmd/xeng` | the cross-engine comparison |

## 3. The profile, and why not the obvious one

The obvious profile is `BenchmarkTapeReplay` on `bench-v1.obt`. That is the tape the
gate times, so it would be judged on the data it was trained on, and any gain would be
an upper bound, not a result.

- **The profile that counts (out-of-sample):** `cmd/xeng`'s `BenchmarkSelfReplay`, which
  replays the other tape, `bench-basic-v1.obt`, through the text adapter. It differs
  from `bench-v1` in its order mix (limit GTC and cancels only) and includes adapter
  parsing that the gate's benchmarks never run.
- **The in-sample profile** (`bench-v1` replay) is measured as well and reported beside
  it, labelled as the upper bound. It decides nothing.

Both profiles are captured on the same M4, and their commands are recorded in §6. The
out-of-sample one is committed as `internal/benchgate/testdata/pgo/basic-selfreplay.pprof`
so a CI dispatch can use it. That file is a measurement input, not an adoption: no
`default.pgo` exists unless §5 passes.

## 4. How it is measured

- **The judge is the gate's.** `cmd/benchgate compare` gets one opt-in flag,
  `-head-pgo <file>`, which adds `-pgo=<file>` to the **head** arm's `go test -c` only.
  Base and head are the same commit, so the only difference between the arms is the
  profile. Everything else is unchanged: interleaved pairs, the probe before every run,
  the k-th order-statistic bound, and the digest check that both arms produced the
  same output on the tape.
- **The flag is never used on push or pull_request.** No workflow passes it on those
  events. A `workflow_dispatch` input, `head_pgo`, passes a committed profile path so
  the same measurement can run on CI's go1.27, which builds the wheels and `obgw`'s
  image.
- **The digest check doubles as the correctness check.** PGO may change inlining, not
  results. If the digests differ, that is a compiler bug and is reported as one.
- **Benchmarks judged:** the four whose timing the gate enforces
  (`Engine_CancelReplaceInto`, `Engine_MatchInto`, `TapeReplay/sink=nil`,
  `OrderBook_LevelChurn`). Everything else the gate runs is reported, not judged.
- **Runs:** locally on the M4 (go1.23.5), three `compare` runs per profile. On CI, three
  dispatches with the out-of-sample profile. The ratio reported is head ÷ base, so
  below 1 is faster.

## 5. The decision rule, before the data

PGO is adopted (a `default.pgo` committed in each binary of §2's table) only if, with
the **out-of-sample** profile:

1. **Faster where it counts:** at least one of the four judged benchmarks has a median
   ratio ≤ 0.95 in every run, locally and on CI.
2. **Slower nowhere:** none of the four has a median ratio above 1.02 in any run.
3. **Same answers:** every digest agrees.
4. **Allocations unchanged** for every gated benchmark.

If it fails, the flag stays, as a tool for the next attempt, and §6 records the numbers.
No profile is committed. "PGO was tried and measured at x" is a result the
documentation can state.

If adopted:

- **The profile is regenerated by a command, never edited.** A `make pgo` target
  reruns §3's out-of-sample capture and writes the same file to each binary's
  directory. A stale profile only loses benefit; Go tolerates one that no longer
  matches the code.
- **Binary size is recorded,** before and after, for `obgw` and `libobook`.
- **The wheels get it for free,** since their build compiles `cmd/libobook`.

## 6. Results

Measured 2026-10-25. Ratios are head ÷ base medians from the judge, so below 1 is
faster. "—" means the judge called that benchmark inconclusive twice (too many tainted
pairs), which is not a measurement.

### 6.1 Profiles

- **Out-of-sample:** `go test -run '^$' -bench 'BenchmarkSelfReplay$' -benchtime 10s
  -cpuprofile basic.pprof` in `cmd/xeng`, committed as
  `internal/benchgate/testdata/pgo/basic-selfreplay.pprof`.
- **In-sample:** the same in `internal/benchgate` with
  `-bench 'BenchmarkTapeReplay/sink=nil$'`. Not committed.
- Most of both profiles is the Go runtime: allocation, GC and scheduling. PGO reshapes
  the call graph of this repository's code, which is the smaller share.

### 6.2 CI, go1.27, out-of-sample profile (the runs that decide)

Three dispatches at `d054885`, base and head the same commit, all on AMD EPYC 7763
([40213607364](https://github.com/intrepidkarthi/orderbook/actions/runs/40213607364),
[40213610055](https://github.com/intrepidkarthi/orderbook/actions/runs/40213610055),
[40213612777](https://github.com/intrepidkarthi/orderbook/actions/runs/40213612777)):

| Benchmark | Run 1 | Run 2 | Run 3 |
|---|---:|---:|---:|
| `Engine_CancelReplaceInto` | 0.980 | 0.968 | 0.961 |
| `Engine_MatchInto` | 0.998 | 0.994 | 0.997 |
| `TapeReplay/sink=nil` | 0.953 | 0.954 | 0.969 |
| `OrderBook_LevelChurn` | 1.004 | 0.998 | 1.016 |

Digests agreed in all three, and allocations were unchanged.

### 6.3 Local, M4, go1.23.5

| Benchmark | Out-of-sample, 3 runs | In-sample, 3 runs |
|---|---|---|
| `Engine_CancelReplaceInto` | —, 0.896, 0.895 | —, —, 0.877 |
| `Engine_MatchInto` | 0.972, —, 0.946 | —, —, 0.908 |
| `TapeReplay/sink=nil` | 0.964, —, — | —, —, 0.921 |
| `OrderBook_LevelChurn` | 1.005, —, 0.984 | 0.968, 0.971, 0.987 |

The laptop tainted half the cells. Where it measured, gains are larger than on CI, and
the in-sample profile does a little better than the out-of-sample one, as §3 expected.
Digests agreed in all six runs.

### 6.4 Against the rule

1. **Fails.** No benchmark reached 0.95 in every run. The closest is
   `TapeReplay/sink=nil` on CI at 0.953-0.969.
2. Holds: the worst ratio is 1.016.
3. Holds: every digest agreed, in nine runs.
4. Holds.

**Not adopted.** No `default.pgo` is committed. The rule was set before the data, and
it is not moved now that the data is close to it.

### 6.5 What this says

- **PGO is worth about 2-5% on the engine's hot paths on CI's toolchain**, and nothing
  on `Engine_MatchInto` or `OrderBook_LevelChurn`. The result is too small to be worth a
  profile to keep fresh in four binaries.
- **It is also below what the gate can see.** The detection floor is 1.2-1.5×, so a
  regression of the size PGO wins back would pass the gate unnoticed.
- **The gain is capped by the runtime's share of the profile.** Larger gains need less
  allocation and fewer pointers for the GC to scan: M11's arena and hot/cold
  experiments, not compiler flags.
- `-head-pgo` and the `head_pgo` dispatch input stay, so a later Go release or a
  changed profile can be re-measured with one dispatch.
